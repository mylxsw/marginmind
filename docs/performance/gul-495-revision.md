# GUL-495：工作区重建修复与待完成验收

## 已验证的原因与修复

旧版每次 onPageChanged 都更新 WorkspaceState，直接或通过父组件更新重建工作区、阅读器、脑图、侧栏和 AppMenus。对提交 53821a9 运行新增的完整应用回归测试：连续 19 次 recordPage，五个组件各重建 19 次。修复后同一测试均为 0。这里统计的是 widget 构建次数，不是 Release 帧耗时，不能据此断言这就是用户卡顿的全部原因。

即时页码移到 readingPagesProvider，只有工具栏和页码浮层按文档订阅。工作区组件和菜单选择其使用的状态字段；标题只订阅 title。保存内容后，若标签、选区与活动文档未变，控制器保留原 WorkspaceState。workspaceContentProvider 忽略只有 lastPage/lastReadAt 变化的内容通知，保留上次展示内容；编辑控制器和资料库仍读取真实仓库。该投影依赖不可变内容列表的身份保留，当前 FileLibraryStore 和 StudySetEditor 符合此约定；若未来仓库重新反序列化全部对象，只会多重建，不会漏掉编辑。

测试还使用真实 FileLibraryStore 和 300 个新增脑图节点：800 ms 防抖保存后，重开磁盘仓库验证 lastPage，资料库 lastPosition 同时更新，五个组件均不重建。新增节点仍能刷新脑图、侧栏和菜单。该测试禁用 PDF 原生渲染，专门验证应用状态与磁盘通知链路。

⌘0 只在当前焦点对应的原生菜单项注册：阅读器为实际大小，脑图为适应窗口；不再同时注册两个 key equivalent。组件测试检查两个焦点方向的 enabled 状态和 shortcut 注册情况。overlay 缓存命中也会移至末尾，使 16 页淘汰策略成为 LRU。

## 尚未满足的合并条件

当前执行环境可运行 macOS 构建和自动化输入，但没有本地操作者提供物理触控板操作。桌面工具的菜单快捷键操作可能直接调用菜单项，因此不能用它证明 NSMenu 的真实按键匹配。以下仍待实机人工采样：

1. 在同一台 Retina Mac、同一份图片型或扫描 PDF、同一份几百节点脑图上，比较 53821a9 与本修订版本。完整应用采用 profile 构建，全屏、分屏模式。使用正常入口 `flutter run -d macos --profile`，不使用 mm_pdf/benchmark 入口。
2. DevTools Performance 记录连续触控板滚动、慢速阅读（每页停留超过 800 ms）、双指缩放。分别保留冷/热轮次、UI/raster 帧时及 timeline，计算 p95；目标不超过 16.67 ms。记录机器、DPR、窗口像素、样本页数与操作时段，不能只截取空闲帧。
3. 同步录制操作前后视频，检查白页、模糊页停留、跳页与手感。FrameTiming 没有涵盖异步光栅化完成延迟，低帧时不能替代这一检查。
4. 阅读器放大后按物理 ⌘0，应回到实际大小；点击脑图并改变视口后按 ⌘0，应适应窗口。来回切换焦点重复验证，确认禁用菜单项不截获快捷键，并检查文本编辑焦点。

先前 gul-495-results.md 和视频仅作为孤立渲染基准保留，不作为这些条件的完成证明。当前 PR 不应合并。
