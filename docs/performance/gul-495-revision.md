# GUL-495：工作区重建修复与待完成验收

## 已验证的原因与修复

旧版每次 onPageChanged 都更新 WorkspaceState，直接或通过父组件更新重建工作区、阅读器、脑图、侧栏和 AppMenus。对提交 53821a9 运行新增的完整应用回归测试：连续 19 次 recordPage，五个组件各重建 19 次。修复后同一测试均为 0。这里统计的是 widget 构建次数，不是 Release 帧耗时，不能据此断言这就是用户卡顿的全部原因。

即时页码移到 readingPagesProvider，只有工具栏和页码浮层按文档订阅。工作区组件和菜单选择其使用的状态字段；标题只订阅 title。保存内容后，若标签、选区与活动文档未变，控制器保留这些字段的身份；展示投影从控制器的最新内容快照派生，保持主线的异步内容更新顺序。workspaceContentProvider 忽略只有 lastPage/lastReadAt 变化的内容通知，保留上次展示内容；编辑控制器和资料库仍读取真实仓库。该投影依赖不可变内容列表的身份保留，当前 FileLibraryStore 和 StudySetEditor 符合此约定；若未来仓库重新反序列化全部对象，只会多重建，不会漏掉编辑。

测试还使用真实 FileLibraryStore 和 300 个新增脑图节点：800 ms 防抖保存后，重开磁盘仓库验证 lastPage，资料库 lastPosition 同时更新，五个组件均不重建。新增节点仍能刷新脑图、侧栏和菜单。该测试禁用 PDF 原生渲染，专门验证应用状态与磁盘通知链路。

⌘0 只在当前焦点对应的原生菜单项注册：阅读器为实际大小，脑图为适应窗口；不再同时注册两个 key equivalent。组件测试检查两个焦点方向的 enabled 状态和 shortcut 注册情况。overlay 缓存命中也会移至末尾，使 16 页淘汰策略成为 LRU。

rebase 后全仓 7 套测试通过（应用 219 项、mm_pdf 31 项），总覆盖率 91.64%；相对最新 main 的可执行改动行覆盖率 98.71%（382/387）。format、analyze、正常 macOS Release 构建与 Python 工具测试均通过。共享缓存、原生菜单注册、导航/搜索/书签和翻页重建均有回归测试。完整应用 Release 采样结果见下方链接。
