# 跨设备同步：实现状态与协议

关联 GUL-604。用户已确认修订方案，实施按“本地基础 → 服务接入 → 多设备验收”推进。

## 当前交付边界

目前已实现协议、合并、安全撤销、可恢复仓库提交，以及学习集远端接收与合并发布 API。
**尚未开启云端同步，也没有配置或上传任何用户账号数据。** 默认资料库继续使用现有本地模式；
显式提供 `FileSyncLedger` 后才启用日志模式，重启从身份文件恢复。应用还没有提供开启同步的界面。

## 内容与设备状态

文件格式 11 的 `StudySetContent` 继续作为本地模型。同步投影把集合按稳定 ID 编码为字典；
节点使用 `(mapId, cardId)`，译文缓存使用 `(documentId, targetLang)`，排期使用 `cardId`。
笔记章节和块分别保存 `items` 与 `order`，正文修改不因数组位置变化而寻址到另一条记录。
未知集合、重复身份与字典键/实体 ID 不一致均拒绝解析。

`sharedContent` 排除阅读位置、最近阅读时间、折叠状态、复习三组数据、助手执行回执及本机对照配置。
`materializeShared` 恢复本机阅读与折叠状态、保留独立管理的复习数据。复习事件、生词和新译文存储的
专用合并协议在后续接入中实现；当前投影里的 `translationCaches` 仅是旧格式缓存。
日志已经分开保存 `sets/<id>`、`reading/<id>/<device>`、`reviews/<id>`、`vocabulary` 和
`translations/<set>/<document>/<language>`。复习流当前仍是旧模型快照，尚未实现事件协议及重放；
译文流保存段落及 origin，不保存任务 job 状态。不能仅凭数据分流就宣称领域合并已完成。

## 三方合并

- 一端未变时接收另一端；相同变化只保留一份；不同字段递归合并。
- 同字段不同值、删除与编辑并发、相同 ID 的不同新增记录产生显式冲突。
- `updatedAt`/`organizedAt` 只合并展示时间，不决定正文胜负，也不用于判断因果。
- 有序笔记块的独立插入合并为稳定顺序；两端相互矛盾的顺序保留为冲突。
- 脑图同排序值使用稳定卡片 ID 作为第二排序键。合并后校验环、父节点、图/卡片/文档引用、
  关系线、概要（含概要节点的子节点）、书签、研究笔记关联及文本标注 revision；
  还校验批注的文档/节点、笔记中指向摘录/自有内容的活引用和章节交叉引用。

`ContentMergeResult.content` 是预览。字段冲突保留基线值，同时返回包含双方候选的 `SyncConflict`；
结构校验失败则 `content == null`。调用者必须先保存冲突及输入版本，不能将预览当成无冲突的提交。
当前合并函数处理一个原子输入单元；后续引擎负责按业务事务分组，让无关事务继续同步。
没有共同祖先、或有多个最大共同祖先时，调用者必须保留分支，不能随意选一个基线。

## 安全撤销

每次本地操作记录前后字段差异。撤销与重做在仓库最新快照上校验预期值，然后一次性应用全部差异；
任何字段或引用约束不满足都不发布候选内容。事务只组合本地操作，不把操作间到达的远端变更纳入历史。
连续修改同一字段会合并，避免每次按键都永久保存一个完整正文副本。
校验容忍当前数据或原操作目标中已有的旧引用错误，但不能因后来加入的内容制造新错误。
解码不运行旧文件的概要自动修复，避免合并/撤销悄悄制造新的卡片。

阅读与复习不进入撤销；修改时间不是撤销前提。撤销新建父节点时，如果它被后来新增的节点引用，
会拒绝该步，以免制造孤立节点。既有菜单和历史工具栏通过 `UndoneNotice.conflict` 显示本地化提示。
工作区还监听共享历史的冲突事件，覆盖忽略返回 notice 的 HUD 和原生菜单入口。
取消事务遇到冲突时，保留已提交内容与条件历史、结束事务并提示，避免编辑状态关闭后历史永久锁住。

## 提交与日志

协议候选版本为 1，尚未发布为长期兼容承诺。提交包含：

```
protocol, id, libraryId, scope, deviceId, sequence, parents, deleted, payload
```

`id` 是按字典键排序后的提交体 SHA-256；`parents` 排序并拒绝重复。对象不可变，读入重新校验摘要。
删除提交只能携带空 payload。账号密码、token、系统密钥不属于此结构。
`SyncGraph` 拒绝缺失父提交、跨资料库/数据域父引用，以及同设备序号分叉。比较版本使用祖先关系，
时间戳不参与版本胜负。多个共同祖先显式返回集合，避免隐藏 criss-cross 分支。

日志按 `SHA256([libraryId, scope])` 隔离，存储在指定根目录下的 `.foliarc-sync/`。
每条提交先写同目录临时文件、flush、rename；未完成的临时文件不属于已提交数据。
重启读取全部已提交文件并校验因果图，损坏数据报错，不能静默覆盖或当作空资料库。
`pending()` 返回未确认的已提交版本；`acknowledge()` 只保存交付确认，不删除合并所需的历史。
调用者必须在云端确认持久化后确认交付，不能在 iCloud 本机暂存成功后确认。

当前日志采用单实例串行所有权；原生多进程、多实例写入不在本批承诺范围。
文件 flush + rename 覆盖进程中断恢复，不把它宣传成所有文件系统的掉电事务保证。
原生端仍要求一个资料库由同一 ledger 实例管理；应用启动时把它同时传给学习集与生词仓库，
译文仓库由学习集仓库传递该实例。并发原生进程写入尚不支持。

### 真实仓库提交与恢复

`.foliarc-sync/identity.json` 固定资料库及设备身份；缺失身份但已有日志时拒绝降级为普通本地模式。
身份不匹配会停止写入，不能把另一账号或资料库的队列接过来。服务账号绑定仍需在接入层实现。

`.foliarc-sync/local/<hash>.json` 是本机事务事实，包含顺序、前驱、多个数据域的本地完整快照及
新生成的共享提交。**这些日志文件不能上传**；发送端只读取 `pending()` 返回的共享提交。
无需另写 outbox；本地状态和待发送版本要么一起存在，要么都未提交。仅本机字段变化可以更新本地快照，
不产生共享内容提交。`expected` 版本前提与领域校验在同一队列内执行，过期候选不允许覆盖当前版本。

原生端以 flush + rename 为提交点；Web 把记录与 `.head` 比较标记放在同一个 IndexedDB 事务内，
防止旧标签页在过期版本上另开分支。事务提交之后的 `.mmset`、生词 JSON、译文 JSONL 写入失败，
不会把已经提交的操作误报为失败；错误保存在 `projectionErrors`，读取和重启使用日志中的数据。
学习集和生词在加载时重建投影；译文读取日志，后续写入或整理时重建文件。

创建、元信息、内容与删除都已改成提交后发布内存和通知。文档包先准备不可变附件，再提交元数据；
提交后的投影失败不会回滚已经被引用的附件。删除学习集时，内容、阅读、复习及已知译文墓碑同事务记录，
保留附件供后续恢复；删除文档也同步记录相关译文墓碑。子数据范围在 ledger 提交队列内确定，
覆盖排队期间刚创建的译文，不能先取快照再异步删除。译文写入在同一队列中再次检查文档生命周期，
拒绝迟到写入复活已删除内容。普通本地模式仍按既有策略删除文件包。

原有资料库首次进入日志模式会建立学习集及已有译文基线；生词首次加载/保存时建立基线。
初始化中的可重试投影/译文基线错误可查询，产品开启流程必须展示并处理这些错误，不能假装全部初始化成功。
当前保留所有本地历史；压缩、其他领域的远端应用、跨设备事件去重及规模测试仍未完成。

### 远端接收与学习集应用

本机日志新记录使用版本 2，仍能重放第一、二批的版本 1；旧客户端拒绝版本 2。
接收记录保留不可变远端提交，允许乱序到达，不把“收到”当成“应用”。随后根据完整祖先关系计算候选，
学习集写队列中的提交再校验预期本地 revision；若已经变化，就从日志中的最新快照重新合并。
成功后再更新资料库内存并通知 `watch`，投影失败保持已提交结果，重启可恢复。

快进直接采用已有远端版本，不制造回声上传；并发独立修改生成引用双方父版本的新提交。
待发送列表只包含本机新生成的版本。处理候选时先尝试后代，再处理祖先，避免已收到合并结果时
仍为旧父版本制造交叉合并；坏的或缺少祖先的后代也不能隐藏可应用的祖先。

缺失祖先、无共同祖先、多个共同祖先、设备身份分叉、删除/编辑、字段或结构冲突均保留输入。
诊断跟随日志持久化；重复输入不重复生成诊断，已纳入成功结果的诊断在同一提交中清除。
未知提交若使用本机设备身份则拒绝接收；其他设备的异常分支保留诊断，不阻止在已接受谱系上继续本机编辑。
阅读位置、复习和本机显示状态不被内容应用覆盖；文档 revision 改变后不沿用旧阅读锚点。
远端文档、图片及研究快照引用必须是包内相对路径；资源解析也拒绝路径穿越及跨平台绝对路径。

`canApply` 提供编辑期间暂缓应用的入口，当前尚未接入应用编辑会话/同步调度器。
**此 API 仍不是完整同步引擎**：只应用 `sets/` 领域，其他领域收到后保留但不发布；
尚未具备文件夹、生词、译文、阅读和复习的远端领域处理器、资源可用性门禁及用户冲突解决界面。
目前可以隔离不同学习集，但同学习集冲突事务之后的独立修改仍可能等待；后续必须增加事务级隔离和
可传播的冲突状态，不能仅把一部分内容标成已合并而丢失尚未处理分支的因果与候选。
